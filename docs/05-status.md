## Not done / blocked
* **Android app (M5-M7):** no Android SDK in the sandbox and Gradle cannot download from Maven Central here, so `:app`
  (UI, session service, SAF provider, instrumented tests) cannot be built or verified. The JVM core is ready for it.
* **Real-VeraCrypt fixtures + cryptsetup oracle:** fixtures are generated by our own Python implementation of the format.
  `tools/verify_fixtures_cryptsetup.sh` must be run on a machine with kernel crypto (AF_ALG) and desktop-VeraCrypt containers
  added before release. Whirlpool/Streebog/cascade/Serpent fixtures are missing for the same reason.
* Write-back sector cache (`CachedBlockDevice`): I/O is write-through; throughput below makes it optional for now.
* Mutation/fuzz/Kover gates, CI workflows, CLI `fsck`, FAT dirty bit, Windows `chkdsk`/desktop VeraCrypt manual gate.

## Measured (desktop JVM, 4 cores; phone numbers still required)
* One 500 000-iteration derivation: SHA-512 0.6 s, SHA-256 0.9 s, BLAKE2s 1.3 s, Whirlpool 3.5 s, Streebog 5.6 s.
  A wrong-password full auto-detect (5 PRFs x 4 header locations) is ~47 s single-threaded, ~12 s with 4 threads here.
  => `Prf.COMMON` (SHA-512, SHA-256, BLAKE2s) exists for a fast default; offer "try all algorithms" as an explicit option.
* FAT32-in-XTS container: sequential read ~250-300 MB/s, write ~70 MB/s (targets on phone: 40 / 25 MB/s).

## PRD errata discovered while implementing
1. **Keyfile order does not matter** (each file restarts at pool position 0, results are added); PRD §6.6/FR-U1 say it does.
2. **HMAC zero-pads short keys**: passwords differing only by trailing 0x00 bytes derive the same key (as in VeraCrypt).
3. **The "derive once, test normal + hidden header" optimisation (§6.3) is impossible**: each header has its own salt.
4. **FAT32 needs >= 65 525 clusters** (~33 MB at 512 B clusters): the PRD's 2-5 MB FAT32 fixtures cannot exist; small fixtures are FAT16/FAT12.
5. B1-B4, M1-M8 findings from `03-development-plan.md` stand; B1 (hidden-volume protection) is implemented and tested.

## TrueCrypt mode (added on request, 2026-11-18)
Supported: magic `TRUE`, header versions 4 and 5, AES-XTS only, PRFs RIPEMD-160 (2000 iterations), SHA-512 (1000), Whirlpool (1000),
no PIM, keyfiles (same algorithm), hidden volumes and backup headers, hidden-volume protection. Selected explicitly (CLI `--truecrypt`,
Android "TrueCrypt mode" checkbox); a container is never auto-detected as TrueCrypt (deniability).
NOT supported: Serpent/Twofish/cascades, LRW/CBC (TrueCrypt < 5), header versions < 4, SHA-1.
Caveats: the iteration counts, header versions and v4 "sector size 0" handling come from the TrueCrypt documentation as remembered
and from our own generator; no real TrueCrypt container has been tested yet. If a real container fails, report its TrueCrypt version and cipher.
